# Проверка воспроизводимости

Проверено 28 октября 2026 года. Среда: Go 1.27.3, macOS arm64, Docker Desktop 29.5.2, Docker Compose 5.1.4, PostgreSQL 18.6. Для интеграционных тестов использована отдельная БД с парольной аутентификацией и владельцем с DDL/CREATEROLE.

## Локальные команды

Команды выполнены в чистой Git-копии в ASCII-каталоге, без исходных `.env`, бинарей и данных БД. Перед запуском Compose скопирован `.env.example`; создан новый именованный том. Результаты относятся к этому прогону, а не к произвольному окружению или будущим версиям зависимостей.

| Команда | Результат |
| --- | --- |
| make generate-check | PASS: DTO совпадают с OpenAPI |
| make vet | PASS |
| make test | PASS, включая HTTP-контракты и безопасную диагностику мигратора |
| make race | PASS |
| make integration | PASS: race, integration-тег, count=1, отдельная PostgreSQL |
| make build | PASS: server и migrate |
| make vuln | PASS: govulncheck v1.9.0, No vulnerabilities found |
| make deploy-check | PASS: полный контейнерный сценарий |
| make generate | PASS: повторная генерация не изменила DTO |
| make smoke | PASS на запущенном Compose-сервисе |
| make fuzz | PASS: по 20 секунд для JSON и нормализации MD5, parallel=2 |

Дополнительно выполнен отдельный подробный интеграционный прогон `cmd/migrate`. Неверный пароль дал connect_database / authentication_failed / 28P01; несовместимая схема при status, up и down — check_schema / schema_mismatch; отсутствующая роль — grant_runtime_role / runtime_role_missing; ошибка применения SQL — apply_migration / postgresql / 42P07. После создания роли повторный up выдал права. После устранения расхождения схемы status снова прошёл.

Синтетические секреты в DSN, пароле, именах схемы, колонки и роли не попали в JSON-логи. Unit-тест с Error(), вызывающим panic, проверяет отсутствие форматирования исходной ошибки. Поля Message, Detail, Hint, Where, InternalQuery и имена объектов PgError не выводятся. У локально выявленной ошибки SQLSTATE не выдумывается.

В первой чистой копии тест паники ошибочно распознал слово private в системном пути `/private/tmp` как содержимое паники. Проверка исправлена на поиск полного panic payload; проверки стека, request_id, статуса и отсутствия хеша сохранены. После исправления полный прогон завершился успешно.

## Запуск и сохранность данных

- Команды быстрого запуска создали PostgreSQL, runtime-роль, миграцию и приложение; `/health/ready` вернул 200.
- Curl-примеры README: POST — 201 с Location; GET — 200 с созданной записью; PUT — 200 с новым именем и сброшенными необязательными полями. Проверены 400 для неверного MD5, 404 для отсутствующего и 409 для повторного POST.
- После `docker compose down` и `docker compose up --build -d` запись, created_at и updated_at совпали с сохранённым ответом. Том при down не удалялся.
- `docker compose stop app` отправил SIGTERM: в логе появились server stopping и server stopped, exit code — 0. Интеграционный тест отдельно проверил остановку с активным SQL и его отмену при исчерпании бюджета.
- Команды migrate status и повторного up прошли. В собранном контейнере отдельно подтверждены безопасные логи неправильного пароля, отсутствующей роли и несовместимой схемы; процесс возвращал код 1.
- Нативные команды из operations выполнены с отдельной БД: go run запустил сервер и readiness; собранный bin/server корректно завершился по SIGTERM с кодом 0. При SIGINT всей группе go run оболочка Go вернула 1, сам сервер записал server stopped; для проверки кода завершения используется бинарь.
- TLS override из operations проверен с временным сертификатом с SAN localhost/127.0.0.1: HTTPS-readiness и GET прошли с проверкой доверия через curl --cacert.

Deploy-check дополнительно проверил пароли со спецсимволами, 40 конкурентных readiness-проб без 429, nonroot/read-only runtime, повторный up/build, отказ и восстановление БД без замены процесса приложения, Bearer, бизнес-rate-limit, недоступный TLS-ключ и bootstrap с пустыми паролями. Созданные им ресурсы удалены.

Локальные Markdown-ссылки README/docs проверены на существование файлов, внешние ссылки badge/workflow — HTTP-запросами с переходом по редиректам. Локальный результат не заменяет удалённый CI: статус конкретного коммита доступен в [GitHub Actions](https://github.com/maxmashevsky-bit/threatservice-go/actions/workflows/ci.yml).

## Ограничения

Короткие fuzz-прогоны и конечный набор негативных сценариев не доказывают отсутствие всех ошибок. Нагрузочный SLA, длительный soak-тест и восстановление из резервной копии в этот прогон не входят. Результат vuln действителен для базы уязвимостей на момент проверки.

Readiness может отражать состояние до отказа или восстановления в пределах TTL 1 секунду. Контекст ограничивает штатную проверку pgx, но не гарантирует точный момент ответа при задержке планировщика или подтверждении отмены драйвером. Проверка схемы не доказывает семантическую эквивалентность CHECK после произвольных изменений владельцем с сохранением имён и колонок. Потеря сети около COMMIT может оставить результат записи неизвестным; автоматических повторов POST/PUT нет. Конкурентный PUT допускает перезапись предыдущего изменения, поскольку в исходном контракте нет версий и If-Match.
