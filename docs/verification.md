# Результаты проверки

Проверено 28 октября 2026 года. Ниже приведены фактические результаты локального запуска. Предельная производительность, промышленный SLA и успешный запуск удалённого GitHub CI не заявляются.

## Сборка и тесты

Среда: Go 1.27.3, macOS arm64, отдельная PostgreSQL 18.1. Интеграционные тесты создают случайные схемы и удаляют только свои объекты. Роль тестового владельца имеет DDL и CREATEROLE, поэтому проверки прав также выполнены.

```sh
TEST_DATABASE_URL='postgres://.../threats_test?...' go test -race -count=1 -timeout=90s -tags=integration ./...
go vet -tags=integration ./...
make generate-check
make build
make vuln
make fuzz
make deploy-check
```

Итог: 43 обычных теста верхнего уровня и 108 их подслучаев прошли. Дополнительно прошли два fuzz-набора с 15 исходными примерами. Всего — 45 наборов верхнего уровня и 123 вложенных запуска; ошибок и пропущенных тестов нет. Пакеты без собственных тестовых файлов проверены сборкой и vet, а код PostgreSQL и миграций — интеграционными тестами.

20 интеграционных наборов верхнего уровня проверяют репозиторий, миграции, права, выбранную схему, старт и остановку сервера. В их числе: 20 конкурентных созданий одного MD5, конкурентные замены и чтения, незавершённая вставка, заблокированный PUT, ожидание пула, пять отмен SQL с повторным использованием того же backend, 11 видов расхождения схемы, удаление целевой таблицы/схемы, temp-объекты и ожидание migration lock.

После обновления Go повторно выполнены fuzz-прогоны с двумя worker и бюджетом 20 секунд на цель:

| Цель | Обработано входов | Результат |
| --- | ---: | --- |
| Строгий JSON, `FuzzDecodeObject` | 19 319 | PASS |
| MD5 и соответствие регулярному выражению OpenAPI, `FuzzNormalizeMD5` | 1 463 280 | PASS |

Результаты fuzz зависят от найденного корпуса, планировщика и доступного CPU. Эти числа не являются пропускной способностью HTTP-сервиса и не доказывают отсутствие ошибок на всех входах.

OpenAPI проверен `kin-openapi`: документ и ссылки корректны, 35 примеров сообщений соответствуют схемам; дополнительные положительные и отрицательные проверки схем прошли. Повторная генерация `oapi-codegen v2.8.0` совпала с сохранёнными DTO. SQL прошёл синтаксический разбор PostgreSQL-парсером и реально выполнялся в интеграционных тестах.

## Исправления по результатам аудита

- Разбор длинного Authorization больше не создаёт массив из всех слов. На фиксированном заголовке около 64 КиБ прежний код выделял 516 099 байт на отказ; регрессионный тест теперь требует не более 1 КиБ. Аналогичная проверка защищает маршрутизацию пути с большим числом разделителей.
- Runtime-запросы явно используют выбранную схему PostgreSQL. Удаление её объектов и переподключение не открывают записи из следующей схемы в search_path или временной таблицы.
- Readiness и повторный up проверяют фактические таблицы, ограничения и необходимые права, а не только номер миграции. Readiness согласован с миграциями через разделяемую advisory-блокировку. Автоматического исправления чужого DDL нет.
- Мигратор корректно экранирует роль и схему, запрещает app-role для status/down, проверяет защиту down до соединения с БД и сообщает о частичном успехе при сбое выдачи прав. Повторный up после исправления роли проверен.
- Проверены границы token68 и переполнение суммы REQUEST_TIMEOUT + 10s. Нерабочая конфигурация отклоняется до старта HTTP.
- Пароли Compose передаются отдельно от URI. На новом томе явно пустой пароль блокирует bootstrap; отсутствующая переменная сохраняет документированный dev-default.
- Обновлены Go 1.27.0 → 1.27.3 и golang.org/x/text v0.29.0 → v0.41.0; вместе с x/text обновлена транзитивная x/sync. До обновления govulncheck сообщил о девяти достижимых уязвимостях, после него `govulncheck v1.9.0` завершился с `No vulnerabilities found`. Основание для исправленных версий: [GO-2026-6809](https://pkg.go.dev/vuln/GO-2026-6809) и [GO-2026-6629](https://pkg.go.dev/vuln/GO-2026-6629); остальные находки стандартной библиотеки также закрыты выбранным Go. Это результат по базе Go на дату запуска, а не бессрочная гарантия.

## Работающий сервис и Docker

Docker Desktop 29.5.2, PostgreSQL 18.6 в контейнере, образ приложения собран на Go 1.27.3. `make deploy-check` прошёл на отдельном случайном Compose project в ASCII-каталоге. Проверены:

- Первый bootstrap с паролями, содержащими `:@/?#%$`, пробел и одинарную кавычку; повторный up со сборкой сохраняет запись и обе даты.
- UID 65532:65532 и read-only root filesystem; приложение стартует только после успешной миграции.
- Неверная конфигурация, ошибки CLI, защита destructive down, отказ и восстановление выдачи прав без потери данных.
- При остановленной БД: liveness 200, readiness 503, запись — безопасный 500. После старта БД тот же процесс приложения снова читает исходную запись; неуспешная вставка не появилась позже.
- Ответы 401 без токена, успешное чтение с токеном и 429 при исчерпании квоты. Токен в проверяемые логи не попал.
- Недоступный UID ключ блокирует старт; доступные PEM-файлы обеспечивают HTTPS с проверкой доверия клиента.
- Пустые owner/app passwords на новом томе блокируют bootstrap; приложение не запускается, проверяемые логи не раскрывают пароль.
- Скрипт удаляет собственные контейнеры, том, образ и временный каталог.

При первичной проверке также выполнены smoke-сценарии на локальном и контейнерном приложении, цикл compose down/up с сохранением тома, проверка отказа недоверенного TLS-сертификата и запрет прикладной роли на DELETE, TRUNCATE, ALTER, DROP и изменение леджера. Актуальный код дополнительно прошёл описанные выше автоматические проверки после обновления Go.

ASCII-путь нужен для воспроизводимого обхода ошибки BuildKit с кириллицей в полном пути. Сертификаты, реальные пароли, бинарники и журналы тестового окружения в архив не включаются.

Полная матрица проверяемого поведения и границы гарантий находятся в [error-scenarios.md](error-scenarios.md).
