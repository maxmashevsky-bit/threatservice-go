# Сопровождение

## Развёртывание и пароли

Если BuildKit сообщает об ошибке `x-docker-expose-session-sharedkey` с `non-ASCII`, перенесите проект в полный ASCII-путь. Кириллица в родительском каталоге также влияет на сборку.

В локальном Compose PostgreSQL доступна только во внутренней сети. Приложение работает под UID/GID 65532 и ролью threat_app; мигратор использует threat_owner. Runtime-роль получает USAGE на схему, SELECT/INSERT/UPDATE на threats и SELECT на schema_migrations. Сервер проверяет схему, но не выполняет DDL.

Для другого окружения задайте отдельные случайные пароли, API_TOKEN и TLS. `.env`, ключи и сертификаты исключены из Git и Docker-контекста. Пароль передаётся отдельно через PGPASSWORD, а не в URI. В `.env` заключайте значения в одинарные кавычки для сохранения буквального `$`; кавычка внутри значения записывается как `\'`. Символы `:@/?#%$` и пробелы не требуют URL-кодирования. Dev-default используется только для отсутствующего пароля; явно пустой пароль на новом томе блокирует bootstrap.

Инициализация ролей выполняется только при создании тома. Изменение `.env` не меняет пароль существующей роли. Если bootstrap оборвался после создания каталога БД, init-скрипты автоматически не повторятся: исправьте роли административным подключением. Пересоздавайте dev-том только при отсутствии нужных данных.

```sh
docker compose logs -f app
docker compose run --rm migrate status
docker compose run --rm migrate -app-role=threat_app up
docker compose down
```

Миграции встроены в бинарь. Флаг app-role поддерживается только перед up; роль должна существовать, не владеть таблицами и не иметь административных привилегий. Схема и выдача прав фиксируются отдельно: если выдача прав не удалась, исправьте роль и повторите up. CLI явно сообщает об этом состоянии. Down удаляет угрозы и требует ALLOW_DESTRUCTIVE_MIGRATION=1; для рабочей БД сначала нужна резервная копия.

Без Docker создайте роли и БД заранее, выполните `go run ./cmd/migrate -app-role=threat_app up` с DSN владельца, затем `go run ./cmd/server` с DSN runtime-роли.

## TLS и остановка

Смонтируйте PEM-файлы read-only, доступные UID 65532. Например, дополнительный `compose.tls.yaml`:

```yaml
services:
  app:
    environment:
      TLS_CERT_FILE: /run/tls/server.crt
      TLS_KEY_FILE: /run/tls/server.key
    volumes:
      - ./certs/server.crt:/run/tls/server.crt:ro
      - ./certs/server.key:/run/tls/server.key:ro
```

Запуск: `docker compose -f compose.yaml -f compose.tls.yaml up --build -d`. Используйте https://localhost:8080, сертификат с соответствующим SAN и при собственном CA — `curl --cacert <ca.crt>`. Нечитаемая или некорректная пара PEM блокирует старт. Для внешней БД используйте DSN с sslmode=verify-full; локальный Compose использует sslmode=disable в закрытой сети.

SIGTERM прекращает приём новых соединений и даёт активным запросам SHUTDOWN_TIMEOUT. При истечении срока запросы отменяются. Compose stop_grace_period по умолчанию 15 секунд при shutdown-бюджете 10 секунд; сохраняйте запас при увеличении настроек. Подтверждение SQL-отмены может занять до дополнительных 250 мс. Потеря соединения около COMMIT не позволяет достоверно определить результат записи; автоматических повторов POST/PUT нет.

## Readiness

GET /health/live не обращается к БД и не зависит от готовности хранилища. GET /health/ready возвращает 200 либо 503. Rate limit бизнес-API не применяется к health-маршрутам.

У каждого процесса один кеш readiness. Успех и ошибка сохраняются на 1 секунду с момента завершения проверки. После истечения TTL устаревший результат не отдаётся: первый запрос запускает новую проверку, остальные ждут тот же результат. Одновременных циклов проверки не больше одного; между завершением и следующим запуском проходит минимум 1 секунда. Один цикл включает Ping и проверку схемы с несколькими SQL-запросами; это не ограничение «один SQL в секунду».

Дедлайн общей проверки — min(1s, REQUEST_TIMEOUT); обращения к БД также учитывают QUERY_TIMEOUT. Драйверу может понадобиться время на подтверждение отмены. Проверка выполняется в одной временной горутине и обязана соблюдать контекст; штатная реализация использует context-aware pgx. Отмена или deadline HTTP-запроса прекращает его ожидание и даёт 503, не отменяя общую проверку для других источников мониторинга. Проверка может кратко продолжаться после отмены всех ожидающих запросов, до собственного deadline. Дополнительные горутины для ожидания каждого запроса не создаются.

Во время TTL успешный ответ может ещё отражать состояние до отказа БД; неуспешный — до восстановления. Устаревший успех не продлевается без повторной проверки. Частота опроса сама по себе не вызывает 429. В нескольких репликах кеши независимы.

## Диагностика

JSON-логи пишутся в stdout. HTTP-ответ содержит серверный X-Request-ID. Неожиданные ошибки дают отдельное ERROR-событие с request_id, operation, cause_category и, для распознанной ошибки PostgreSQL, SQLSTATE. INFO-событие завершения запроса содержит тот же request_id, операцию, статус и длительность.

| Категория | Надёжно распознаваемое основание |
| --- | --- |
| context_canceled | errors.Is(context.Canceled) |
| deadline_exceeded | errors.Is(context.DeadlineExceeded), при необходимости вместе с SQLSTATE 57014 |
| database_unavailable | pgconn.ConnectError; SQLSTATE класса 08, 57P01/57P02/57P03 или 53300 |
| postgresql | Остальные PgError; код логируется только в формате пяти заглавных ASCII-букв/цифр |
| network | net.OpError без доказанного подключения к БД |
| internal | Причина не определена по безопасным типизированным признакам |
| panic | Перехваченная паника |

Нераспознанные ошибки не классифицируются по тексту. Не логируются err.Error(), поля Message/Detail/Hint/Where/InternalQuery PostgreSQL, имена таблиц и ограничений, DSN, параметры SQL, заголовки авторизации и тела запросов. Исключение — фиксированные сообщения проверки конфигурации, не содержащие значений переменных. Стек паники включает до 64 символических кадров: функции, исходные файлы и строки; значения аргументов и panic payload не записываются. Паника внутри общей readiness-проверки также публикует 503 и освобождает ожидающих.

При старте operation показывает этап: parse_database_config, initialize_database_pool, connect_database, check_schema, resolve_schema, load_tls или listen_http. Здесь ещё нет HTTP-запроса и request_id. Причина классифицируется до замены ошибки безопасным сообщением. Сообщения net/http до создания запроса могут содержать чужой протокольный ввод: они заменяются событием http_transport без исходного текста. Это ограничивает подробность TLS/transport-диагностики, сохраняя конфиденциальность.

## Проверки

Контрактные тесты загружают api/openapi.yaml и запускают ручной handler через httptest. Для корректных запросов проверяется схема входа; для отрицательных сценариев — ожидаемый отказ без требования валидности входа. Для ответов проверяются конкретный статус, application/json, наличие заявленных заголовков и JSON-схема. Контрольные мутации подтверждают обнаружение неверного статуса, Content-Type, пропущенных заголовков и обязательных полей. Авторизация отдельно проверяется существующими HTTP-тестами; контрактные сценарии используют профиль без токена. Валидатор kin-openapi нужен только тестам и не включён в обработку запросов.

`make integration` использует TEST_DATABASE_URL отдельной БД, создаёт случайные схемы и удаляет только их. Для проверок прав нужен CREATEROLE; без него соответствующие тесты пропускаются явно. `make deploy-check` создаёт случайный Compose project в ASCII-каталоге и проверяет конкурентный readiness, bootstrap, пароли со спецсимволами, повторную сборку, сохранность данных, отказ/восстановление БД, Bearer/rate limit, nonroot/TLS и ошибки CLI. Его ресурсы удаляются после завершения.

`make smoke` проверяет работающий экземпляр, создаёт случайную запись и оставляет её в БД: DELETE в исходном API отсутствует. Для другого адреса задайте BASE_URL и при необходимости API_TOKEN. Fuzz-прогоны запускаются отдельно через make fuzz; они не заменяют контрактные и интеграционные тесты.
