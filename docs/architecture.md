# Устройство сервиса и принятые решения

## Границы задачи

Сервис принимает уже известные сведения об угрозе, хранит их по MD5 и отдаёт другим клиентам. Он не принимает файлы, не вычисляет их хеши, не выполняет антивирусный анализ и не проверяет истинность присланной оценки. MD5 сохранён из исходного API; коллизии этого алгоритма не позволяют использовать его как доказательство идентичности или безопасности файла.

Обязательный контракт: `POST /info`, `GET /info/{md5}`, `PUT /info/{md5}`. Дополнения к модели и защите ниже укладываются в указанные в задании улучшения. Поиск, список, удаление, очереди, кеш записей, gRPC, отдельный сервис авторизации и история изменений для трёх операций не требуются.

## Компоненты

Один Go-процесс обслуживает HTTP через стандартную библиотеку и использует пул `pgx` для PostgreSQL. Слои разделены по ответственности:

- HTTP: маршрутизация, строгий разбор JSON, ограничения тела, Bearer-токен, rate limit, преобразование результата в HTTP-ответ.
- `internal/threat`: модель, проверка полей и сценарии создания, чтения и замены. Репозиторий задан интерфейсом.
- Репозиторий PostgreSQL: SQL, атомарность, перевод ошибок отсутствующей записи и уникальности в ошибки предметной области.
- Миграции: отдельная команда и встроенные SQL-файлы. Сервер проверяет версию схемы перед приёмом запросов.

Память процесса не является источником данных. Перезапуск не теряет записи. Отдельные реплики сервера могут использовать одну БД; блокировки и уникальность обеспечиваются в PostgreSQL. Это не обещает отказоустойчивости самой БД: репликация, резервное копирование и восстановление относятся к инфраструктуре окружения.

Redis и брокер сообщений не используются: нет фоновых задач, а кеширование текущих записей добавило бы протокол инвалидирования. PostgreSQL одновременно решает хранение, уникальность и сериализацию замены записи. Отдельный gRPC-интерфейс не добавлен, потому что исходное задание требует REST.

## Модель и валидация

| Поле | Назначение и правило |
| --- | --- |
| `md5` | Ключ записи; ровно 32 шестнадцатеричных ASCII-символа, хранится в нижнем регистре |
| `name` | Название угрозы; 1–255 кодовых точек Unicode, не только пробелы, без NUL |
| `description` | Пояснение клиента; до 4 000 кодовых точек, без NUL; по умолчанию пустая строка |
| `severity` | Оценка клиента: `unknown`, `low`, `medium`, `high`, `critical`; по умолчанию `unknown` |
| `created_at` | Серверное время создания; UTC, не меняется при замене |
| `updated_at` | Серверное время последнего фактического изменения; не раньше `created_at` |

Дополнительные поля запроса необязательны, поэтому исходные минимальные примеры с `md5` и `name` остаются допустимыми. Клиентские даты не принимаются. Строки не обрезаются и не приводятся к Unicode NFC: это сохранило бы уже переданные клиентом данные с изменениями. Для пустого имени используется `strings.TrimSpace`; длины измеряются в кодовых точках, а не байтах.

HTTP принимает один UTF-8 JSON-объект до 65 536 байт. Обязательные поля нельзя пропустить; `null`, неизвестные и повторные ключи, неправильный регистр имён полей и дополнительное JSON-значение запрещены. `Content-Type` — `application/json` с необязательным UTF-8 charset. Сжатые тела не поддерживаются. Защита от избыточного тела действует до предметной валидации.

## Хранение и конкурентный доступ

Основная таблица `threats` содержит текущую версию шести полей. Первичный ключ по нормализованному MD5 обеспечивает поиск и уникальность. Проверки в БД дополнительно ограничивают допустимые значения и даты; они не заменяют проверку с понятным ответом на уровне приложения. Индексы по `name`, `severity` и датам не нужны без соответствующих запросов. Леджер миграций используется мигратором и проверкой версии при старте.

`POST` выполняет вставку с ограничением уникальности. В гонке нескольких запросов одного MD5 только один получает `201`; остальные — `409`, независимо от регистра хеша и совпадения остальных полей. Конструкция «сначала проверить, затем вставить» не используется.

`PUT` заменяет все изменяемые поля существующей записи. Это не upsert: неизвестный MD5 возвращает `404`. Отсутствующие необязательные поля сбрасываются в значения по умолчанию. Проверка текущих значений и замена выполняются с защитой строки от конкурентных обновлений. При равенстве всех значений возвращается текущая запись с прежним `updated_at`; при изменении `updated_at` вычисляется по серверному времени, а `created_at` сохраняется. Строгий рост `updated_at` между заменами не гарантируется: операции могут получить одинаковую временную метку. Поле не используется как версия записи.

Конкурентные замены одной записи сериализуются. В API нет номера версии или `If-Match`, поэтому последняя выполненная замена может затереть предыдущую. Это осознанный предел исходного контракта; при требовании защиты от потерянного изменения следует отдельно добавить optimistic locking и документировать конфликт версии.

Сервер отвечает после выполнения операции БД. При query deadline драйвер отправляет отмену и ожидает подтверждения PostgreSQL с ограничением 250 мс; это предотвращает позднее выполнение ожидающего блокировку запроса на доступной БД. Разрыв соединения или deadline около фиксации не позволяют достоверно заключить, произошла ли запись: ответ `500` не доказывает откат. `GET` после такой ошибки показывает текущее состояние и не доказывает, какая из конкурентных операций его создала. Повтор `POST` может дать `409`. Повтор одинакового `PUT` не меняет данные и дату, если между повторами не было чужой замены; иначе повтор может затереть её. Автоматические повторы записывающих запросов на сервере не выполняются.

## Схема и права

Мигратор имеет права владельца. Он сериализует изменение схемы на стороне PostgreSQL и ведёт историю применённых миграций; SQL встроен в бинарь, чтобы файл образа и миграции не расходились. При `up` параметр `-app-role=threat_app` выдаёт приложению права работы с таблицей и чтения леджера. Роль сервера не получает DDL или право удалять угрозы.

В Docker Compose роль приложения создаётся при первом старте PostgreSQL. Пароль передаётся в `psql` как переменная и вставляется через экранируемый SQL-литерал `:'app_password'`, а не через конкатенацию SQL. Явно пустой `APP_DB_PASSWORD` завершает init-скрипт с ошибкой; пустой пароль владельца отклоняет официальный entrypoint PostgreSQL. Dev-значения применяются только к отсутствующим переменным. Для подключения пароль передаётся отдельно через стандартный `PGPASSWORD`, который pgx использует при отсутствии пароля в URI. Поэтому специальные символы не меняют структуру DSN. В `.env` пароли следует заключать в одинарные кавычки для сохранения буквального `$`.

Отдельная one-shot-команда применяет миграции до запуска приложения. Уже созданный том не инициализируется повторно; изменение паролей требует явного администрирования БД. Если первичная инициализация оборвалась после создания каталога данных, PostgreSQL при следующем старте не повторит init-скрипты: исправьте роли вручную либо пересоздайте только этот dev-том, если в нём нет нужных данных. Неуспешная миграция блокирует запуск приложения.

## Защита и эксплуатация

Опциональный Bearer-токен подходит для небольшого обмена между доверенными сервисами. Непустой `API_TOKEN` должен содержать от 16 до 1024 ASCII-символов в формате token68. Пустой токен оставлен для совместимости с локальными примерами; для открытой сети токен и TLS необходимо настроить. Токен не описывает отдельных пользователей или роли и не даёт аудит действий по пользователю. Ни токен, ни DSN, ни содержимое запросов не должны попадать в логи.

Опциональный общий token bucket ограничивает бизнес-запросы в пределах одного процесса. Глобальная квота для кластера потребовала бы внешнего координатора; здесь это лишняя зависимость. Не используется IP из переданного клиентом `X-Forwarded-For`.

Встроенный TLS настраивается парой PEM-файлов. Сертификаты хранятся вне образа и монтируются read-only. Внешняя TLS-терминация также возможна, но её доверенные прокси и сетевая политика относятся к развёртыванию. Локальный Compose публикует только HTTP на loopback, БД остаётся внутри сети Compose.

У HTTP и SQL есть deadlines, у соединений — ограниченный пул. При остановке по сигналу сервер завершает текущие запросы в заданный срок. По умолчанию `SHUTDOWN_TIMEOUT` равен 10 секундам, а Compose `stop_grace_period` — 15 секундам. При изменении первого параметра второй должен оставаться больше него с запасом, иначе Docker может завершить процесс раньше окончания graceful shutdown.

Внутренние ошибки диагностируются структурированными ERROR-событиями с безопасной категорией и SQLSTATE. Readiness использует кеш результата на 1 секунду и объединяет одновременные проверки; liveness от БД не зависит. Дедлайны, отмена ожидания, состав логов и эксплуатационные настройки описаны в [operations.md](operations.md).

Архив сдачи называется `Машевский_Максим_Go.zip`, внутри исходники размещены в ASCII-каталоге `threatservice`. Для Docker-сборки используйте полный путь без кириллицы, например `~/threatservice` при ASCII-имени домашнего каталога. На некоторых конфигурациях BuildKit кириллица в родительском пути вызывает ошибку передачи заголовка `x-docker-expose-session-sharedkey` с `non-ASCII`; перенос всего проекта в ASCII-путь устраняет эту проблему окружения.

Число RPS и задержка не заявлены без измерений на зафиксированном стенде. Основной рабочий запрос — поиск по первичному ключу. Возможные ограничения при росте — число соединений, I/O БД и горячая строка при частых `PUT` одного MD5. Перед масштабированием следует измерить нагрузку с ожидаемым соотношением чтения и записи; метрики и распределённая трассировка добавляются по требованиям окружения.

## Проверки

Unit- и HTTP-тесты проверяют валидацию, значения по умолчанию, ошибки, строгий JSON и вспомогательные middleware без БД. Интеграционные тесты используют PostgreSQL: реальные ограничения, повторы, даты, параллельные вставки и замены, миграции. Детектор гонок проверяет конкурентный Go-код, но не подменяет проверку SQL на настоящей БД. Контрактные HTTP-тесты сверяют ручные обработчики с OpenAPI через kin-openapi и входят в обычный make test и CI. Проверка generate-check отдельно сравнивает сгенерированные DTO; эти проверки дополняют друг друга.

`scripts/smoke.sh` проверяет готовый HTTP-сервис с отдельной случайной записью. Это дополнительная проверка связки компонентов, а не нагрузочное испытание. Исходный контракт и его уточнения находятся в `api/openapi.yaml`.

## Совместимость схемы и границы восстановления

Пул закрепляет первую доступную прикладную схему из исходного `search_path`; запросы репозитория явно указывают эту схему. Удаление таблицы или схемы не переключает сервис на одноимённые объекты из следующей схемы либо временные таблицы. Для намеренной смены схемы требуется новая конфигурация и перезапуск. Миграции закрепляют целевую схему внутри транзакции. Readiness использует разделяемую advisory-блокировку, а `up` и `down` — исключительную: новая проверка ожидает незавершённую миграцию в пределах deadline. Уже закешированный результат может отражать состояние до начала миграции только в пределах TTL 1 секунду.

Проверяется версия, состав и типы колонок, NOT NULL, значения по умолчанию, первичный ключ, collation MD5, отсутствие RLS и пользовательских триггеров, наличие валидированных CHECK с ожидаемыми именами и колонками, а также права чтения и записи. `up` при обнаружении несовместимой схемы останавливается и не исправляет DDL автоматически. Эта проверка выявляет эксплуатационное расхождение схемы; она не доказывает семантическую эквивалентность CHECK после произвольных изменений владельцем БД с сохранением имён и набора колонок. Владелец схемы остаётся доверенной административной ролью.

После SQL-отмены на доступном сервере проверяется подтверждение отмены, чтобы она не затронула следующий запрос на том же соединении. Потеря сети около COMMIT может оставить результат записи неизвестным. Автоматических повторов POST и PUT нет; GET показывает текущее состояние, но не устанавливает автора изменения при конкурентном доступе. Сохранность при повреждении диска, аварии хоста или ошибочном удалении тома требует резервного копирования на уровне эксплуатации.
