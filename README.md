# Сервис обмена информацией об угрозах

REST-сервис на Go хранит сведения об угрозах по MD5 в PostgreSQL. Реализованы три операции исходного API: создание записи, получение по MD5 и полная замена изменяемых полей существующей записи. Модель дополнена описанием, уровнем опасности и серверными датами.

Сервис принимает сведения клиента: он не сканирует файлы и не подтверждает достоверность оценки. Отсутствие записи и значение `unknown` не означают, что файл безопасен. MD5 используется как ключ исходного контракта; коллизии не позволяют считать его доказательством идентичности файлов.

## Запуск через Docker Compose

Нужны запущенный Docker Engine или Docker Desktop, Docker Compose v2 или новее, Git и curl 7.71 или новее. Локально устанавливать Go и PostgreSQL для этого способа не требуется. Порт 8080 должен быть свободен.

```sh
git clone https://github.com/maxmashevsky-bit/threatservice-go.git "$HOME/threatservice-go"
cd "$HOME/threatservice-go"
cp .env.example .env
docker compose config --quiet
docker compose up --build -d
docker compose ps -a
docker compose logs migrate
curl --fail --retry 10 --retry-connrefused --retry-delay 1 --max-time 3 \
  http://127.0.0.1:8080/health/ready
```

Ожидаемый ответ готовности: `{"status":"ok"}`. Команды выполняются из корня проекта. При сборке используйте полный путь без кириллицы: некоторые конфигурации BuildKit отклоняют такой путь с ошибкой `x-docker-expose-session-sharedkey` / `non-ASCII`.

Compose последовательно запускает PostgreSQL 18, дожидается готовности TCP-подключения, выполняет мигратор и запускает приложение после успешной миграции. HTTP опубликован на `127.0.0.1:8080`; порт PostgreSQL наружу не опубликован. Приложение работает под UID/GID 65532, с файловой системой read-only и без Linux capabilities.

```sh
docker compose logs -f app
docker compose down
```

`down` останавливает сервисы и сохраняет именованный том `pgdata`. Повторный `up` использует прежние записи. Значения паролей в примере предназначены для локального запуска; для другого окружения задайте собственные пароли, Bearer-токен и TLS.

## Запуск без Docker

Нужны Go 1.27.3 или новее и работающая PostgreSQL 18. Пример предполагает доступ к административной роли `postgres` и серверу БД на `127.0.0.1:5432`; при необходимости замените адрес и имя администратора.

```sh
psql -h 127.0.0.1 -U postgres -d postgres
```

В открывшейся сессии создайте роли, задайте им пароли интерактивно и создайте БД:

```sql
CREATE ROLE threat_owner LOGIN;
CREATE ROLE threat_app LOGIN;
\password threat_owner
\password threat_app
CREATE DATABASE threats OWNER threat_owner;
\q
```

Затем из каталога проекта примените миграцию от владельца и запустите сервер от прикладной роли. Подставьте пароли, заданные выше:

```sh
export DATABASE_URL='postgres://threat_owner@127.0.0.1:5432/threats?sslmode=disable'
export PGPASSWORD='replace-with-owner-password'
go run ./cmd/migrate -app-role=threat_app up

export DATABASE_URL='postgres://threat_app@127.0.0.1:5432/threats?sslmode=disable'
export PGPASSWORD='replace-with-app-password'
export HTTP_ADDR='127.0.0.1:8080'
go run ./cmd/server
```

Файл `.env` читает Compose; самостоятельный Go-процесс получает только переменные окружения. Он не создаёт БД, роли или таблицы при старте. При несовместимой схеме запуск прекращается.

Для сборки отдельных бинарников выполните `make build`: команды появятся в `bin/server` и `bin/migrate`. `make run` запускает сервер с уже заданным окружением; `make up` и `make down` соответствуют запуску и остановке Compose.

## Настройки

| Переменная | Значение по умолчанию | Назначение |
| --- | --- | --- |
| `DATABASE_URL` | обязательна | DSN PostgreSQL для конкретного процесса |
| `PGPASSWORD` | нет | Пароль подключения, если он не задан в DSN |
| `HTTP_ADDR` | `:8080` | Адрес сервера; в локальном Compose порт опубликован только на loopback |
| `PG_MAX_CONNS` | `10` | Максимальное число соединений пула, положительное целое |
| `REQUEST_TIMEOUT` | `3s` | Deadline обработки HTTP-запроса |
| `QUERY_TIMEOUT` | `2s` | Deadline обращения к БД, включая ожидание соединения; не больше REQUEST_TIMEOUT |
| `SHUTDOWN_TIMEOUT` | `10s` | Бюджет завершения активных запросов и закрытия пула |
| `API_TOKEN` | пусто | Общий Bearer-токен; пустое значение отключает авторизацию |
| `RATE_LIMIT_RPS` | `0` | Общий лимит бизнес-запросов на процесс; 0 отключает |
| `RATE_LIMIT_BURST` | `20` | Вместимость token bucket, положительное целое |
| `TLS_CERT_FILE` | пусто | Путь к PEM-сертификату |
| `TLS_KEY_FILE` | пусто | Путь к PEM-ключу; задаётся вместе с сертификатом |

Длительности задаются в формате Go, например `500ms` или `3s`. RATE_LIMIT_RPS должен быть конечным неотрицательным числом. API_TOKEN принимает 16–1024 ASCII-символа token68: буквы, цифры, `-._~+/` и необязательные завершающие `=`. Пробелы и управляющие символы запрещены. Некорректная конфигурация блокирует старт.

Compose дополнительно читает `POSTGRES_PASSWORD` и `APP_DB_PASSWORD`; по умолчанию — `dev-owner-change-me` и `dev-app-change-me`. URI и имена ролей заданы в compose.yaml, пароли передаются отдельно через PGPASSWORD. Пример настроек в `.env`:

```dotenv
POSTGRES_PASSWORD='replace-with-owner-password'
APP_DB_PASSWORD='replace-with-app-password'
API_TOKEN='replace-with-random-token-32-chars'
RATE_LIMIT_RPS=20
RATE_LIMIT_BURST=40
PG_MAX_CONNS=10
REQUEST_TIMEOUT=3s
QUERY_TIMEOUT=2s
SHUTDOWN_TIMEOUT=10s
```

Одинарные кавычки сохраняют буквальные `$`, `#` и пробелы; кавычка внутри такого значения записывается как `\'`. Пароли, передаваемые отдельно от URI, не требуют URL-кодирования. Отсутствующий пароль использует dev-default, явно пустой пароль блокирует первичную инициализацию БД. Изменение `.env` не меняет пароль уже созданной роли.

TLS-пути передаются непосредственно процессу или через Compose overlay из раздела ниже: базовый compose.yaml их не устанавливает. `.env`, ключи, сертификаты, бинарники и логи исключены из Git и контекста сборки.

## Примеры API

Контракт с моделями, заголовками и примерами описан в [api/openapi.yaml](api/openapi.yaml). Примеры ниже соответствуют локальному запуску без токена. При включённой авторизации добавьте к каждой бизнес-операции `-H "Authorization: Bearer $API_TOKEN"`; для HTTPS используйте соответствующий адрес и доверенный CA.

### Создание

```sh
curl -i http://127.0.0.1:8080/info \
  -H 'Content-Type: application/json' \
  --data '{"md5":"0123456789ABCDEF0123456789ABCDEF","name":"Trojan.Win32.Generic","description":"Получает команды с удалённого узла","severity":"high"}'
```

Ответ — `201 Created`, `Location: /info/0123456789abcdef0123456789abcdef` и JSON, например:

```json
{
  "md5": "0123456789abcdef0123456789abcdef",
  "name": "Trojan.Win32.Generic",
  "description": "Получает команды с удалённого узла",
  "severity": "high",
  "created_at": "2026-10-28T12:00:00Z",
  "updated_at": "2026-10-28T12:00:00Z"
}
```

Повтор этой команды возвращает `409 Conflict` и `{"message":"Threat already exists"}`.

### Получение

```sh
curl -i http://127.0.0.1:8080/info/0123456789abcdef0123456789abcdef
```

Ответ — `200 OK` с текущей записью. До её изменения тело соответствует примеру создания:

```json
{
  "md5": "0123456789abcdef0123456789abcdef",
  "name": "Trojan.Win32.Generic",
  "description": "Получает команды с удалённого узла",
  "severity": "high",
  "created_at": "2026-10-28T12:00:00Z",
  "updated_at": "2026-10-28T12:00:00Z"
}
```

Для отсутствующего MD5 ответ — `404 Not Found` с сообщением `Threat not found` и безопасным уточнением в details.

### Полная замена

```sh
curl -i -X PUT http://127.0.0.1:8080/info/0123456789abcdef0123456789abcdef \
  -H 'Content-Type: application/json' \
  --data '{"name":"Trojan.Win32.Updated"}'
```

Ответ — `200 OK`. Пропущенные description и severity сбрасываются в значения по умолчанию; created_at сохраняется:

```json
{
  "md5": "0123456789abcdef0123456789abcdef",
  "name": "Trojan.Win32.Updated",
  "description": "",
  "severity": "unknown",
  "created_at": "2026-10-28T12:00:00Z",
  "updated_at": "2026-10-28T12:10:00Z"
}
```

Даты в примерах условные: фактические значения назначает PostgreSQL. Повтор идентичного PUT сохраняет updated_at. PUT отсутствующей записи возвращает `404`, новая запись не создаётся. MD5 задаётся только в пути, в теле PUT он запрещён.

Пример отказа при неверном входе:

```sh
curl -i http://127.0.0.1:8080/info \
  -H 'Content-Type: application/json' --data '{"md5":"invalid","name":"x"}'
```

Ответ — `400 Bad Request`:

```json
{"message":"Invalid request","details":"md5: must contain exactly 32 hexadecimal characters"}
```

## Модель и правила валидации

| Поле | Тип PostgreSQL | Правило |
| --- | --- | --- |
| `md5` | `varchar(32) COLLATE "C"` | Первичный ключ; 32 ASCII hex-символа; оба регистра допустимы на входе, в БД нижний |
| `name` | `varchar(255) NOT NULL` | Обязательно; 1–255 кодовых точек Unicode, не только пробелы; без NUL |
| `description` | `text NOT NULL DEFAULT ''` | Необязательно; до 4000 кодовых точек Unicode; без NUL |
| `severity` | `varchar(8) NOT NULL DEFAULT 'unknown'` | `unknown`, `low`, `medium`, `high`, `critical` |
| `created_at` | `timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP` | Назначает БД; не меняется при PUT |
| `updated_at` | `timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP` | Не раньше created_at; обновляется при фактическом изменении полей |

Длины строк измеряются в кодовых точках, а не байтах. Пробелы по краям сохраняются, Unicode NFC и регистр имени не нормализуются. Клиентские даты не принимаются. Даты ответа приводятся к UTC с суффиксом Z, точность БД — до микросекунд.

Тело — ровно один UTF-8 JSON-объект, не больше 65 536 байт, включая chunked-передачу. Запрещены null, неизвестные поля, другой регистр имени поля, повторные ключи после декодирования escapes, неверные типы, некорректный UTF-8 и непарные UTF-16 surrogate escapes. Content-Type — application/json с необязательным charset=utf-8. Сжатие не поддерживается; Content-Encoding identity допустим.

## HTTP-статусы и конкурентные запросы

| Статус | Причина |
| --- | --- |
| `200` | GET/PUT выполнен либо health-проверка успешна |
| `201` | POST создал запись; Location указывает на её нормализованный MD5 |
| `400` | Неверные MD5, JSON, обязательные поля или значения |
| `401` | При включённом API_TOKEN нет корректного Bearer-токена; заголовок WWW-Authenticate: Bearer |
| `404` | Запись или маршрут отсутствует |
| `405` | Метод не разрешён; Allow содержит разрешённые методы |
| `409` | POST с уже существующим MD5 |
| `413` | Тело больше 65 536 байт |
| `415` | Неподдерживаемые Content-Type, charset или Content-Encoding |
| `429` | Исчерпан лимит бизнес-API; Retry-After содержит оценку задержки в секундах |
| `500` | Внутренняя ошибка, недоступность БД или deadline бизнес-операции |
| `503` | Readiness-проверка неуспешна либо её ожидание отменено/просрочено |

Ответы приложения имеют Content-Type application/json, Cache-Control: no-store и серверный X-Request-ID. Ошибка содержит message и, при необходимости, безопасное details. Для внутренних ошибок детали отсутствуют. HEAD отклоняется с 405 без тела; автоматических редиректов для слешей и dot-сегментов нет. Query-параметры не используются.

Уникальность MD5 обеспечивает первичный ключ и INSERT ON CONFLICT DO NOTHING. Предварительного запроса «есть ли запись» нет: конкурентные вставки не создают дубликаты, проигравшие конфликту получают 409. Замена выполняется одним UPDATE и блокирует строку; GET читает целую версию без смешения полей разных замен. Все SQL-параметры передаются отдельно от текста запроса.

Последний выполнившийся PUT может затереть предыдущий: номера версии и If-Match в контракте нет. updated_at не является версией и не обязан строго расти при каждом изменении; часы могут сдвигаться, операции могут иметь одинаковые метки. Изменения строки и временных полей атомарны. Автоматических повторов POST и PUT нет: разрыв сети около COMMIT может оставить результат записи неизвестным. GET показывает текущее состояние, но не доказывает, какой конкурентный запрос его записал.

| `internal/config/config.go` | Переменные окружения и проверка настроек |
| `internal/httpapi/http.go` | Маршруты, middleware и вызовы предметных операций |
| `internal/httpapi/transport.go` | Авторизация, чтение тела, HTTP-ответы и преобразование ошибок |
| `internal/httpapi/json.go` | Строгий разбор JSON и проверка Unicode |
| `internal/httpapi/readiness.go` | Кеш готовности и объединение одновременных проверок |
| `internal/threat/threat.go` | Модель, валидация и сервис создания/чтения/замены |
| `internal/postgres/` | Настройка пула, закрепление схемы и SQL репозитория |
| `internal/diagnostic/` | Безопасные категории ошибок, SQLSTATE и символический стек |
| `migrations/` | Встроенный SQL, леджер, блокировки и проверка совместимости схемы |
| `api/` | OpenAPI, сгенерированные DTO и директива генерации |
| `deploy/postgres/10-app-role.sh` | Создание runtime-роли при первом запуске БД |
| `Dockerfile`, `compose.yaml` | Образ и запуск сервисов с зависимостями |

Запрос проходит через определение маршрута и метода, проверку MD5 пути, авторизацию и бизнес-лимитер. Для POST/PUT затем проверяются формат содержимого, размер, Unicode и JSON, после чего DTO преобразуется в Input. Предметный сервис проверяет значения и нормализует MD5; репозиторий получает соединение из ограниченного пула и выполняет SQL. Результат БД преобразуется в DTO ответа, ошибка — в HTTP-статус и безопасную диагностику.

Сервер использует стандартный net/http, pgx/v5 для PostgreSQL и x/time/rate для token bucket. Других сервисов хранения, очередей и координаторов нет. Типы в api/types.gen.go сгенерированы oapi-codegen v2.8.0 и уже включены в исходники; для обычной сборки генератор не нужен. При изменении спецификации обновите типы командой `make generate` или `go generate ./api`.

## База данных и миграции

Таблица threats содержит шесть полей модели. Первичный ключ по MD5 одновременно является индексом уникальности и поиска. Дополнительных индексов нет, поскольку API не ищет по другим полям. CHECK-ограничения проверяют формат MD5, длины, непустое имя, severity и порядок дат; предметная валидация дополнительно проверяет Unicode и пробелы.

Леджер schema_migrations содержит version bigint PRIMARY KEY с CHECK version > 0 и applied_at timestamptz NOT NULL DEFAULT CURRENT_TIMESTAMP. SQL встроен в бинарь через go:embed. Up и down выполняются транзакционно под исключительной advisory-блокировкой; новая проверка готовности использует разделяемую блокировку и ожидает незавершённую миграцию в пределах deadline. Уже закешированный readiness-ответ может отражать прежнее состояние до истечения TTL.

```sh
docker compose run --rm migrate status
docker compose run --rm migrate -app-role=threat_app up
```

Флаги указываются перед командой. App-role допустим только с up; роль должна уже существовать, не владеть таблицами и не иметь административных привилегий. Выдача прав выполняется отдельной транзакцией после миграции. Если она не удалась, схема остаётся применённой: исправьте роль и повторите up. Status проверяет совместимость и необходимые права. Down удаляет threats и все записи; для него требуется явно задать ALLOW_DESTRUCTIVE_MIGRATION=1. Рабочие данные перед этим нужно сохранить.

Мигратор работает владельцем threat_owner. Серверная роль threat_app получает USAGE на схему, SELECT/INSERT/UPDATE на threats и SELECT на schema_migrations; прав на удаление записей, DDL и изменение леджера ей не выдаётся. Init-скрипт запускается только при создании каталога данных и безопасно передаёт пароль через экранированный SQL-литерал psql.

Пул закрепляет выбранную схему, а запросы явно указывают её имя. Удаление таблицы или схемы не переключает репозиторий на одноимённые объекты следующей схемы или temp-таблицы. Старт и readiness проверяют версию, колонки, типы, NOT NULL, defaults, первичный ключ threats, collation MD5, необходимые права, отсутствие RLS/пользовательских триггеров и валидированные CHECK с ожидаемыми именами и колонками. Несовместимый DDL автоматически не исправляется.

Проверка не доказывает семантическую эквивалентность CHECK после произвольной замены выражения администратором с сохранением имён и колонок. Владелец схемы остаётся доверенной ролью. Сохранность при потере хоста или повреждении диска требует резервного копирования; именованный том сам по себе резервной копией не является.

## Авторизация, TLS и диагностика

При непустом API_TOKEN бизнес-запросы требуют `Authorization: Bearer <token>`. Токен сравнивается по хешу в постоянное время; отдельные пользователи, роли доступа и аудит по пользователям не предусмотрены. Бизнес-лимит общий для процесса, не для IP; X-Forwarded-For не используется. У нескольких реплик лимиты независимы.

Для HTTPS смонтируйте сертификат и ключ read-only, доступные UID 65532. Например, сохраните как compose.tls.yaml следующий overlay:

```yaml
services:
  app:
    environment:
      TLS_CERT_FILE: /run/tls/server.crt
      TLS_KEY_FILE: /run/tls/server.key
    volumes:
      - ./certs/server.crt:/run/tls/server.crt:ro
      - ./certs/server.key:/run/tls/server.key:ro
```

```sh
docker compose -f compose.yaml -f compose.tls.yaml up --build -d
curl --fail --retry 10 --retry-all-errors --retry-delay 1 --max-time 3 \
  --cacert certs/ca.crt https://localhost:8080/health/ready
```

Сертификат должен иметь подходящий SAN; ca.crt — доверенный CA, подписавший server.crt. Нечитаемая или некорректная пара PEM блокирует старт. Встроенный TLS допускает версии от 1.2. Для подключения к внешней PostgreSQL используйте DSN с sslmode=verify-full; локальный Compose использует sslmode=disable в своей сети.

JSON-логи идут в stdout. ERROR содержит request_id, operation, cause_category и SQLSTATE при наличии. Категории различают context_canceled, deadline_exceeded, database_unavailable, postgresql, network, internal и panic. INFO завершения содержит тот же request_id, маршрут, операцию, статус и длительность. При старте запрос ещё отсутствует: записывается этап сбоя без request_id.

Произвольный текст ошибок, DSN, пароли, токены, тела, SQL-параметры и чувствительные поля PostgreSQL не записываются. Для panic сохраняются до 64 кадров функций с файлами и строками без значений аргументов и panic payload. Текст транспортных ошибок net/http заменяется безопасным общим событием; это ограничивает подробность их диагностики. Нераспознанные причины остаются категорией internal.

## Health checks, таймауты и остановка

GET /health/live отвечает без обращения к БД. GET /health/ready возвращает 200 с `{"status":"ok"}` либо 503 с `{"message":"Service not ready"}`. Оба маршрута доступны без токена и не расходуют бизнес-квоту.

Успешный и неуспешный результат readiness кешируются на 1 секунду с момента завершения. После TTL первый запрос запускает новую проверку, остальные ожидают тот же результат. Одновременно выполняется не больше одного цикла на процесс; каждый цикл включает Ping и проверку схемы с несколькими SQL-запросами. Частота опроса сама по себе не вызывает 429.

Общая проверка ограничена min(1s, REQUEST_TIMEOUT), обращения к БД — также QUERY_TIMEOUT. Отмена или deadline HTTP-запроса прекращают его ожидание, не отменяя общую проверку для остальных. Проверка использует context-aware pgx и может кратко продолжаться после отмены всех ожидающих. Во время TTL ответ может отражать состояние до отказа или восстановления БД; бесконечно устаревший успех не используется.

HTTP-сервер имеет ReadHeaderTimeout 5s, ReadTimeout 10s, WriteTimeout REQUEST_TIMEOUT + 10s и IdleTimeout 60s. Срок запуска с проверкой БД — 5s, команды мигратора — 30s. SQL-deadline включает ожидание пула и блокировок. Подтверждение отмены PostgreSQL может занять до дополнительных 250 мс.

SIGINT/SIGTERM прекращает приём новых соединений и даёт активным запросам SHUTDOWN_TIMEOUT. После истечения бюджета запросы отменяются, соединения закрываются. В Compose stop_grace_period равен 15s при стандартном shutdown-бюджете 10s; при увеличении бюджета сохраняйте запас до принудительной остановки контейнера.

## Типичные проблемы и ограничения

- Порт 8080 занят: освободите его или измените host-порт в compose.yaml. Для самостоятельного запуска задайте HTTP_ADDR.
- Ошибка BuildKit с non-ASCII: перенесите весь проект в путь без кириллицы, включая родительские каталоги.
- Мигратор не завершился: смотрите `docker compose logs migrate postgres`; проверьте доступ к БД, существование ролей и совместимость схемы. Приложение не запускается до успешной миграции.
- После смены `.env` БД отклоняет пароль: существующий том сохраняет прежние роли и пароли. Меняйте их административным подключением. Не удаляйте рабочий том для исправления пароля.
- Bootstrap оборвался на новом томе: init-скрипты не повторяются автоматически после появления каталога данных. Исправьте роли вручную либо пересоздайте только ненужный dev-том, понимая, что его содержимое будет потеряно.
- TLS не стартует: проверьте пару PEM, SAN и доступ UID 65532 к смонтированным файлам. Переменные TLS из `.env` не передаются базовым Compose без overlay.
- Readiness вернул 503: проверьте логи по request_id; возможны недоступность БД, несовместимая схема, нехватка прав или deadline. Liveness при этом может оставаться 200.

API не содержит списка, поиска, удаления, истории изменений и защиты от потерянного обновления через версии. Производительность и отказоустойчивость зависят от окружения и PostgreSQL. Ошибки транспорта до принятия HTTP-запроса могут не иметь стандартного JSON-ответа.
